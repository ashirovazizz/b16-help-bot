# Архитектура

## Что изменилось относительно исходного ТЗ

Согласовано с заказчиком (А. Аширов) перед разработкой:

| Было в ТЗ | Стало | Зачем |
|---|---|---|
| Любой сотрудник запускает CREATE, ARCHIVE и UPDATE | CREATE и ARCHIVE запускает реестр People, сотрудник — только UPDATE и «снять мою страницу» | Должность и состав команды приходят только от владельца реестра |
| Лист Users с вручную собранными Telegram ID | Одноразовая ссылка-приглашение `t.me/бот?start=код` | Не нужно собирать ID, привязка подтверждается тем, кто отправил ссылку |
| Диалог в чате с сессиями | Веб-форма по подписанной ссылке, открывается с текущим текстом страницы | Удобно править длинный текст, фото в оригинале, нет состояния диалога |
| 9 статусов, «взять» и «начать» — разные шаги | 4 рабочих статуса, у каждого один ответственный; «Беру» только закрепляет | Всегда понятно, чей ход |
| `/published ID URL` | Кнопка «Опубликовано»; адрес спрашивается только у новой страницы | Меньше ручного ввода, снятию URL не нужен |
| Заявитель обязательно подтверждает | Молчание 2 рабочих дня = согласие | Заявки не висят бесконечно |
| Profiles обновляется вручную | Profiles обновляется при закрытии заявки, прошлая версия — в History | Таблица всегда повторяет сайт |
| — | Ежедневная сводка и напоминания | Заменяют память руководителя |
| Apps Script, webhook, журнал эффектов | Node.js на сервере центра, long polling, идемпотентные переходы | Apps Script не умеет отвечать кодом ошибки; на сервере всё проще и надёжнее |
| 7 листов | 5: People, Profiles, Requests, History, Settings | Users слит с People, Sessions не нужен |
| Список редакторов в настройках | Кнопки карточки доступны участникам рабочего чата; взявший заявку её ведёт | Права берутся из того, что уже есть |

## Компоненты

```
             ┌──────────── сервер центра (Docker) ────────────┐
Telegram ◄──►│ бот (grammY, long polling)                      │
             │        │                                         │
Браузер  ◄──►│ форма (Hono) ──► RequestService ──► Repository ──┼──► Google Таблица
             │        │           │  │                           │
             │ планировщик ──────┘  └──► PhotoStore ────────────┼──► Google Drive
             │ (сверка, таймеры, сводка)  SiteChecker ───────────┼──► dh.itmo.ru
             └─────────────────────────────────────────────────┘
```

- `RequestService` — все сценарии. Каждый вызов идёт под общим замком: бот, форма и таймеры не переписывают одни и те же строки одновременно.
- `Repository` — хранилище. Рабочее — Google Таблица, для тестов — память. Если центр когда-нибудь уйдёт с Google, заменяется один модуль.
- `Notifier` — куда писать: карточки в тему «Сайт», личные сообщения, сводка, тревоги.

## Заявка

| Статус | Чей ход | Срок |
|---|---|---|
| Черновик | заявитель | новая страница: напоминание через 2 р. д.; обновление: черновик закрывается через 14 дней |
| У редактора | редактор | публикация за 3 р. д. |
| Нужны данные | заявитель | напоминание через 2 р. д. |
| На проверке | заявитель | через 2 р. д. закрывается как подтверждённая |
| Готово, Отменена, Отклонена | — | — |

Сроки и праздники задаются на листе Settings.

Переходы (`src/domain/workflow.ts`):

- `submit` — заявитель отправил анкету: Черновик / Нужны данные → У редактора;
- `take` — «Беру»: заявка закрепляется за редактором, статус не меняется;
- `needInfo` — вопрос заявителю: У редактора → Нужны данные;
- `publish` — «Опубликовано»: → На проверке (снятие — сразу Готово);
- `confirm` / `autoConfirm` — На проверке → Готово;
- `askFix` — «Нужна правка»: На проверке → Нужны данные, заявитель правит анкету, заявка возвращается тому же редактору;
- `reject`, `cancel`, `expire`, `withdraw` — закрытие без публикации.

Любое действие редактора закрепляет заявку за ним, если она ещё ничья. Чужую заявку другой редактор не трогает. Переназначить: очистить в Requests «Ведёт» и «Ведёт (Telegram ID)».

Повторное нажатие кнопки или повторная отправка формы ничего не ломает: переход проверяет текущий статус.

## Сверка с реестром

Раз в 5 минут (и по команде `/sync@бот` в рабочем чате) бот сравнивает, кто **должен** быть на сайте, с тем, кто **есть** на сайте:

- должен = «Статус: работает» и «Публикуем на сайте: да»;
- есть = в Profiles «Публикация: опубликована».

| Должен | Есть | Что делает бот |
|---|---|---|
| да | нет | заявка «Новая страница» в статусе Черновик; когда человек подключится, бот пришлёт анкету |
| нет | да | заявка «Снятие» сразу редактору; открытые заявки человека отзываются |
| да | да | если висит снятие от реестра — отзывает его |
| нет | нет | если висит черновик новой страницы — отзывает |

Если человек сам снял страницу или отказался от новой, бот ставит в People «Публикуем на сайте: нет» с пометкой в «Примечании». Иначе сверка вернула бы страницу обратно. Больше бот в колонки реестра не пишет: только ID новым строкам, привязку Telegram и ссылку-приглашение.

## Данные

Колонки листов бот ищет по заголовкам, поэтому их можно переставлять и добавлять свои: чужие колонки бот не трогает.

- **People** — реестр: ID, ФИО, Категория, Должность в центре, Статус, Публикуем на сайте, Примечание; служебные: Telegram ID, Telegram, Привязан, Ссылка-приглашение, Приглашение до.
- **Profiles** — зеркало страницы: ID, ФИО, Адрес страницы, Публикация, Подпись, О себе, Проекты и исследования, Курсы, Контакты, Канал, Фото, Обновлено, Заявка.
- **Requests** — заявки: статус, чей ход, срок, кто ведёт, даты и те же поля, что в Profiles. В колонке «Изменено» перечислено, какие поля заявка меняет: пустое значение изменённого поля означает «убрать блок».
- **History** — неизменяемый журнал: каждый переход, привязка, правка реестра, прошлая версия страницы (JSON «было/стало»).
- **Settings** — сроки, время сводки, праздники и перенесённые рабочие дни.

Поля страницы описаны в одном месте — `src/domain/fields.ts`. Если на сайте поменяются блоки, правится только он.

Телефоны, дни рождения и личные почты из старых таблиц в книгу не переносятся: процессу они не нужны.

## Безопасность

- Секреты (токен бота, доступы Google, `LINK_SECRET`) лежат только в `.env` на сервере. В репозитории и журналах их нет.
- Доступ к Google ограничен scope `drive.file`: бот видит только созданные им книгу и папку для фото.
- Ссылка на форму подписана HMAC и привязана к заявке, роли и сроку: подделать или открыть чужую нельзя. Страница формы отдаётся с CSP на nonce, `Referrer-Policy: no-referrer` (токен не утекает по ссылкам), `no-store`.
- Ссылка-приглашение одноразовая: около 128 бит случайности, срок жизни 30 дней. Один Telegram нельзя привязать к двум людям.
- Каждое действие заново сверяется с реестром: ушедший сотрудник теряет доступ сразу, даже с открытой формой.
- В таблицу всё пишется в режиме RAW: формула из анкеты не исполнится.
- Бот работает в рабочем чате с privacy mode и без прав администратора. Кнопки карточек срабатывают только в рабочем чате.

## Надёжность

- Long polling: Telegram отдаёт обновления по одному, входящие порты не нужны.
- Состояние меняется ровно один раз: переход проверяет текущий статус. Уведомления — «хотя бы один раз»: при сбое Telegram заявка не ломается, в тему уходит тревога.
- Запросы к Google повторяются при 429 и 5xx.
- Сбой задачи планировщика вызывает одну тревогу до восстановления.
- Если Telegram недоступен при старте, сервис через минуту завершается с понятной ошибкой, и Docker его перезапускает.
